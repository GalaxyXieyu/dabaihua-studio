# 作者声音（待持续校准）

这是一份给 `writer`、`humanizer` 和 `qa` 使用的项目级声音基线，不是让 Agent 编造个人经历的模板。

## 硬规则：只写我们自己凝练的东西（Yu 定，2026-09-28，优先级高于本文件其他条目）

> Yu 原话：文章写作不要带任何的来源索引；行文里面也不要写什么什么谁说过；应该代入我自己的场景；参考的文章往往只是一些方向，具体可以丰富，然后提炼或者问问我是怎么想的；我们凝练的东西才是我们的，而不是去解读别人的。

1. **正文不带任何来源索引**：不写「参考资料」「延伸阅读」「来源：」「数据来源」、脚注、原文链接、文末出处列表。
2. **不写转述句**：不写「X 说过」「X 认为」「据 X 报道」「X 在博客/笔记/复盘里写道」「某公司指南里记过」。观点用作者自己的判断直接说出来。
3. **案例代入 Yu 自己的场景**：贯穿案例和运行时画面来自 Yu 的团队、工作和实践；缺材料就先问 Yu，不编造经历。
4. **参考文章只当方向**：可以借它丰富细节、帮我们提炼，但文章主线是我们的判断，不是解读、复述或评论别人的文章。
5. **不编造数据照旧**：写进正文的数字必须真实、可核；出处留在 `fact-check.md` 等内部文件里备查，正文不署名。
6. **适用范围**：公众号、知乎等对外文章及其配图、排版。晴儿的每日素材（`daily-topics/`，带链接和摘要）不受影响，照常保留链接。

## 当前基线

- 面向关心 Agent、AI 工具、知识工作和内容生产的中文读者。
- 从具体观察、实际操作或明确判断切入，不先报幕。
- 解释技术时先说它解决的实际问题，再给术语、机制或代码。
- 立场清晰，承认边界；不假装中立，也不编造经历、数据或情绪。
- 语言平实、克制，有必要时使用自然比喻，但不堆金句、对仗或口头禅。
- 文章按“现象 → 运行时画面/例子 → 原因 → 解决方式 → 边界”推进；不先宣布工具价值，再从头铺垫同一问题。
- 技术、架构与工作流文章优先展示真实运行时证据，例如任务状态、依赖、角色、日志、截图或可复现结果。架构图服务于这些证据，使用克制的中性色、细线和少量状态强调，不做装饰性插画。

## 更新方式

每次定稿后，把用户确认“像自己”的段落摘录到 `writer/references/style_examples.md`，并在这里补充可复用的句式、节奏或禁区。不要把未经用户确认的 AI 草稿当成作者样本。
