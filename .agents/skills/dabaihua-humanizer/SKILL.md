# 中文技术文章去 AI 味

面向 AI Agent、VibeCoding、工具实战和开发踩坑文章的编辑 Skill。目标不是把文章改得更口语，也不是追求某个 AI 检测分数，而是让文字像作者真的做过、想过、写过。

## 触发场景

- 用户说“去 AI 味”“人话一点”“改得像我写的”
- 用户觉得稿子“太像 AI”“太抽象”“逻辑不顺”“像宣传稿”
- 对公众号、知乎、技术博客、项目复盘进行人性化改写
- QA 的 L4 活人感检查发现问题，需要返工

## 前置读取

1. Read `content/_config/author-voice.md`，确认作者定位和声音。
2. Read `.agents/skills/writer/references/style_examples.md`，如果文件有真实样稿，提取句长、口语和叙事习惯。
3. Read 待修改文章全文，不先按关键词批量替换。
4. 技术文章优先保留命令、代码、参数、版本、链接、术语、表格和事实，不为“自然”而改错技术含义。

## 核心判断

每次修改先回答三个问题：

1. 这句话提供了新信息，还是只是在宣布作者要讲什么？
2. 这段是在推进真实经历和判断，还是在重复上一段的结论？
3. 这句话像作者基于具体经历说出来的，还是像模型总结出来的标准答案？

如果只是表达方式问题，局部改写；如果是信息重复或顺序不通，调整段落，不要只换同义词。

## 必查的结构级 AI 味

### 1. 重复报幕和重复介绍

重点扫描：

- 同一个工具、项目或观点在相邻段落重复宣布
- “我做了 X”之后又出现“我最近写了 X”
- 先说“这篇要讲什么”，正文又完整说一遍
- “有一点先说清楚”“下面我们来看”“接下来要讲的是”“值得注意的是”后面没有新内容

处理方式：

- 保留一次最自然、最有信息量的介绍
- 删除元叙述，直接进入事实、场景或判断
- 检查段落之间是否真正推进，而不是只换了说法

### 2. 逻辑重叠和重复举例

逐段检查：

- 同一个因果链是否解释了两遍
- 同一个例子是否只换了角色名又出现一次
- 前文已经说明“上下文被挤压”，后文是否又完整复述
- 引出产品前，问题是否已经讲够；引出产品后，不要重新再讲一遍问题
- 开头是否已经给出结论，后文却又从头铺垫同一个问题；这会让文章看似有结构，实际原地绕圈

处理方式：

- 相同信息只保留最具体、最有现场感的一次
- 如果两段承担不同功能，明确区分“现象、原因、解决方式”，否则合并
- 删除无法改变读者理解的重复句

### 3. 否定转折对仗

高风险结构：

- 不是 A，而是 B
- 不在 A，而在 B
- 不仅 A，而且 B
- 这不是……这是……
- 难的不是……而是……

不是看到一次就机械删除。只有在前后形成工整对仗、用于制造“深刻结论”时才优先改。

替代方式：

- 直接说结果：“真上手后，麻烦集中在这几步。”
- 改成因果：“流程一复杂，主 Agent 先被上下文拖住。”
- 改成场景：“轮到启动下一个 Agent 时，上一份结果还没验收。”
- 必须保留对比时，使用具体事实，不写抽象升华。

### 4. 三段式和镜像排比

检查连续出现的：

- “记得 A，却忘了 B；记得 C，却不确定 D”
- “谁在做什么、按什么要求做、最后有没有做对”
- 三个相同句法的总结句
- 每节都用“第一、第二、第三”或三项工整列表

处理方式：

- 保留必要并列，但打散句式
- 两项通常比硬凑三项自然
- 把其中一项换成具体动作、结果或失败现场
- 不为了打散而引入新的空泛口语

### 5. 预告腔、总结腔和升华腔

优先检查：

- “这说明……”“这意味着……”“从更大的角度看……”
- “所以我对它的定位很简单”
- “换句话说”“归根结底”“综上所述”
- 每节末尾都来一句可截图的金句
- “让 X 保持……让 Y 实现……”这类对仗收束

处理方式：

- 结论已经从事实中自然得出时，删掉总结句
- 需要结论时，用作者判断或实际后果收尾
- 技术文章优先写“因此下一步怎么做”，少写抽象意义

### 6. 口语伪装和书面归责腔

高风险表达：

- “错在让……”
- “问题在于……”连续使用
- “你可能会想……”但后文没有回应读者真实疑问
- “它就是一个……”反复下定义
- “显式化、开箱即用、赋能、闭环、抓手、落地”这类脱离具体场景的词

处理方式：

- 直接写现象和动作，不先给句子贴标签
- “错在让……”改成具体后果：流程被挤到上下文后面，跑着跑着就走样
- “问题在于……”反复出现时，改写为具体的发生过程、失败现场或可观察后果
- 术语能换成人话就换，但技术概念需要时保留正式名称
- 不用“说真的”“你想想看”等口语填充物硬装真人

### 7. 抽象概括过多，缺少现场材料

检查每 500-700 字是否至少有一项：

- 真实操作
- 命令或代码
- 截图或界面现象
- 具体错误
- 时间、数量、状态、结果
- 作者做过的选择和放弃的方案

没有材料时，优先删短文章，不用抽象句补长度。

### 8. 抽象架构缺少运行时证据

技术文章常把 Agent、工作流、插件或架构讲成一组抽象能力，读者仍然不知道它实际如何运行。

优先补入真实且可核对的材料：

- 任务状态、依赖关系、执行顺序或验收节点
- Agent 的 Role、Skills、Context、当前 Activity 或日志
- 真实截图、界面现象、命令输出或错误记录
- 架构图与实际界面保持同一种信息语言，重点突出状态、关系和数据流，不用装饰性图标掩盖信息不足

处理方式：

- 先让正文出现一个具体运行时画面，再解释机制或引出工具。
- 图像是证据层，不是重复讲一次正文。若没有可验证材料，缩短抽象承诺，不用“项目主管”“核心价值”等标签补强。

### 9. 作者声音不足

技术文章至少保留适量的：

- 第一手经历：“我为什么开始做它”
- 具体判断：“我会在什么情况下用，什么情况下不用”
- 不确定性或边界：“这部分现在还不稳定”
- 真实反应，但必须具体，不写“非常震撼”“令人印象深刻”

不强行添加情绪、自嘲、疑问句或“我认为”。没有真实依据就不补。

## 修改顺序

1. 先删重复段落和重复介绍。
2. 再修正文段顺序，确保“现象 → 运行时画面/例子 → 原因 → 解决方式 → 适用边界”能顺着读。
3. 再处理否定对仗、三段式、报幕腔和升华句。
4. 最后才改词语、句长和标点。
5. 通读修改后的相邻段落，确认没有因为局部润色产生新的重复。

## 不应修改的内容

- 不凭空添加个人经历、数据、观点或情绪。
- 不为了规避模式而删除必要的技术对比。
- 不把所有“不是”或“而是”都替换掉，避免文章失去正常中文语气。
- 不把技术文章改成短句堆叠或营销文案。
- 不改变命令、代码、参数、版本号、链接、文件名和事实结论，除非用户明确要求。
- 不用同义词循环掩盖重复内容。

## 输出要求

完成后给出：

1. 修改后的文件或正文。
2. 结构级改动摘要，说明删了哪些重复、调整了哪些逻辑。
3. 仍需作者确认的地方，不超过 3 项。

如果只是做诊断，不直接改稿，输出问题位置、问题类型和建议改法。

## 交稿前检查

- [ ] 工具/项目只在必要位置介绍一次
- [ ] 没有连续两段重复同一因果链
- [ ] 没有成组出现的“不是 A，而是 B”式对仗
- [ ] 没有连续镜像句或机械三段式
- [ ] 没有“这篇要讲什么”的元叙述
- [ ] 没有每节固定出现的金句式总结
- [ ] 没有“先宣布结论、后面又重新铺垫同一问题”的循环结构
- [ ] 至少有足够的具体操作、界面、代码、结果或经历；架构类文章优先有运行时状态、依赖或实际界面证据
- [ ] 口语化来自作者真实习惯，不是硬塞口头禅
- [ ] 技术信息和事实没有被润色破坏
