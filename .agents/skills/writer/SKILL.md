# Long Form Writer

写公众号/知乎长文的 Skill。用你自己的声音，不是通用 AI 腔。

> 当前作者声音以 `content/_config/author-voice.md` 和 `references/style_examples.md` 为基线。它们只能收录用户确认的成稿与偏好；缺少第一手经历、核心立场或情绪节点时必须向用户索取，不得用通用 AI 叙事补齐。

---

## 触发场景

- 用户要写一篇新的公众号/知乎长文
- 用户有素材/想法/大纲，让 Claude 帮助写稿
- 用户要续写或扩写已有草稿

---

## 前置步骤（每次必须）

1. 拉取线上策略：
   ```bash
   topics strategy --platform gzh --json > /tmp/gzh-strategy.json
   topics strategy --section banned_patterns --json > /tmp/banned.json
   topics strategy --section cta_templates --json > /tmp/cta.json
   ```
   离线时用 `topics strategy --cached --platform gzh --json`。

2. Read `content/_config/platform-specs.json` 获取平台结构规格；选题路由、标题公式、CTA 和禁用模式仍以 `topics strategy` 输出为准。

3. 如果线上拉取失败，警告用户"策略未拉取，可能用到旧版本"，并询问是否继续。

策略 JSON 包含：
- `positioning`: 平台定位
- `content_routing`: 内容类型路由（工具教程/实战踩坑/判断型/热点借势，以及允许/禁止的类型）
- `title_formulas`: 每种类型的标题公式
- `publish_rules`: 发布规则（单日≤1篇、热点≤48小时、系列导航 footer 等）

写之前先根据 `content_routing` 判断选题属于哪种类型，然后用对应的 `title_formulas`。

## 第一步：理解输入 + HKR 质检

用户可能给你任何形式的输入，包括：素材链接/PDF/语音稿/散乱想法/大纲。

**先判断选题质量，再决定是否动笔。**

HKR 质检框架：
- **H (Hook)**：标题和开头能让人好奇、想继续看吗？
- **K (Knowledge)**：看完能学到什么？有信息增量吗？
- **R (Resonance)**：能戳中情绪？让人"对对对我也这样"？

S级选题三项全有，及格选题至少两项。**只有一项甚至不到一项的，主动跟用户说选题方向可能需要调整。**

如果素材信息不够，主动问用户：
- "你大概想讲哪几个核心点？"
- "有没有自己亲身的经历可以放进去？"
- "是什么让你想到要写这个？"

---

## 第二步：AI 和人的分工

**AI 能做的（放心让 AI 做）：**
- 找证据/类比/支撑素材（给定观点后，找历史、学术、技术上的佐证）
- 提供多个比喻供用户选择
- 按已确认的大纲和角度扩写每个部分
- 补充技术/工具/学科背景知识（LangGraph 原理/Claude API 参数/Agent 架构等）
- 梳理逻辑，检查结构

**必须由用户提供的（AI 不能代替）：**
- 第一手经历和观察（"我用这个工具踩了这个坑"）
- 核心创意角度（那个让文章真正立住的角度，必须是用户自己决定的）
- 个人的真实判断和立场（AI 可以提候选，但"就是这个"必须用户拍板）
- 情绪节点（什么让你兴奋/沮丧/觉得有意思）

**理想协作流程：**
```
你：提供素材 + 核心观点/角度 + 个人经历 + 情绪节点
 ↓
Claude：补充背景知识 + 找证据类比 + 结构建议 + 按角度扩写
 ↓
你：二次修改（加入自己的声音、补充真实细节、打破节奏）
 ↓
Claude：L1-L5 质检 → 输出修改建议
 ↓
你：终审定稿
```

## 第三步（公众号专属）：内容类型路由 + 标题公式

> 只写公众号文章时执行本节；知乎/其他平台跳过。

### 3.1 内容类型路由

先确定这篇属于哪种类型（决定标题写法和结构重心）：

| 类型 | 流量来源 | 标题写法 | 示例 |
|------|---------|---------|------|
| **工具教程/系列课** | 搜一搜（长尾资产） | 含搜索词，动作+工具+场景 | `LangGraph实战：怎么搭多轮对话Agent` |
| **实战分享/踩坑** | 搜一搜+推荐双引 | 问题前置，有亲身时间感 | `用了3个月LangGraph，这几个坑要注意` |
| **判断型/为什么选X** | 推荐算法（CTR最高） | 强立场，制造比较和悬念 | `为什么我放弃了AutoGen，转向LangGraph` |
| **方法论/总结** | 推荐算法 | 结论前置，数字强化 | `我总结的Agent开发3个核心原则` |
| **热点借势** | 推荐（48小时窗口） | 必须+亲测角度，否则不写 | `GPT-5我测了一天，说几个真实体验` |

### 3.2 推荐友好标题公式

**核心结构：`[问题/痛点]？[工具] [实战/解法]`**

✅ 好标题：
- 问题前置：`为什么你的Agent总是跑偏？——5个状态管理错误`
- 结果前置：`用LangGraph 10行代码实现多轮对话，比你想象的简单`
- 数字强化：`LangGraph系列第3课：Checkpoint机制彻底搞懂`

❌ 推荐差的标题：
- 纯术语开头：`LangGraph StateGraph详解`（没有Hook，靠搜索）
- 泛化大词：`AI Agent 终极指南`（无具体工具/场景）
- 太学术：`基于图结构的多智能体协作框架分析`

### 3.3 合集/系列结构规范

如果这篇属于某个系列（如 LangGraph 第N课），必须遵守：

**每篇必须独立成立**（不依赖前一篇，新读者直接看得懂）

**系列文件夹结构：**
```
[系列名]/
├── 00-大纲导读.md   ← 第一篇，永久 pinned，内含完整目录
├── 01-XXX.md
├── 02-XXX.md
└── ...
```

**每篇结尾必须有导航 footer：**
```
---
**[系列名] 全系列：**
- 第0篇 → [大纲导读]（建议先看）
- 第1篇 → [XXX]
- ← 你在这里：第N篇
- 第N+1篇 → [预告/链接]
```

**单日不超过1篇**（一天发多篇会争夺推荐位，只有最好的那篇能出头）

## 第四步：文章类型判断

写之前先确认属于哪种，每种写法重心不同：

**调查实验型**：亲自下场做了一件事，然后报道发现。
- "我替你做了这件事" 是核心
- 写法重心：过程叙事 + 层层递进的发现

**工具体验型**：拿到工具实际使用，带读者一起体验。
- "跟我一起玩" 是核心
- 写法重心：真实场景演示 + 踩坑记录 + 效果展示

**现象解读型**：观察到一个现象，层层深入分析。
- "你注意到了吗？背后是什么？" 是核心
- 写法重心：观察 → 好奇 → 分析 → 洞察/升维

**方法论分享型**：把积累的经验和方法系统性地分享。
- "我把压箱底的东西掏给你了" 是核心
- 写法重心：每节必须有可执行的行动建议；坦诚说明学习成本和常见失败点；不只画饼

## 第五步：你的声音

动笔前先读 `references/style_examples.md`，那是你自己写过的稿子。照着它的样子写，不要套模板。

写作过程中同步执行 `.agents/skills/wechat-draft-editor/SKILL.md`（`wechat-draft-editor`）的结构检查。重点不是堆口语词，而是避免重复报幕、重复介绍、重复因果链、否定转折对仗、机械三段式和每节固定升华。先保证经历、判断和材料真实，再调整句式。

具体要求：
- 同一个工具、项目或插件只在最自然的位置完整介绍一次。后文若需要回指，直接推进它解决的问题、实际限制或使用结果，不再重新宣布“我做了它”或“我最近写了它”。
- 开头从真实事件、操作结果或具体困惑切入，不先解释“这篇文章要讲什么”。先写问题如何出现，再安排场景、机制、工具和解决方式，避免开头先给结论、后文又重新铺垫。
- 一段已经讲过的原因，后文不要换同义词再讲一遍；需要展开时，明确是在补充机制、例子、边界，还是用新的可验证材料推进。
- 对抽象的多 Agent、流程或架构论述，至少补一个可感知的运行时画面，例如任务状态、依赖、截图、日志、角色职责、实际失败或验收结果。不要只靠功能名与概念解释。
- 发现“不是 A，而是 B”“难的不是……而是……”“不在于……而在于……”这类工整对仗时，先判断是否真的需要对比。能直接写现象、因果、场景或实际后果，就不造判断腔。
- 少用“错在让……”“问题在于……”等书面归责句。优先描述发生了什么、为什么会走样、下一步怎么处理。
- 不强行添加“说真的”“你想想看”、自嘲或疑问句。口语感来自真实写作习惯和具体现场。
- 加粗只用于读者必须停下来的术语、结论或操作，不用整句加粗替代结构和论证。

## 第六步：文章结构

**通用结构（可调整）：**
```
【开头】从一个具体事件/场景/问题切入，不宏大叙事
  ↓
【背景铺垫】让不了解这个领域的人也能看懂，但是聊天式的，不是教科书式的
  ↓
【核心内容】每个板块：
  - 一个明确的观点/结论
  - 至少一个具体场景/代码/截图/案例支撑
  - 你自己的判断（不是"有人认为"）
  ↓
【踩坑/边界】什么情况下不适用？什么是常见错误？（诚实是信任的来源）
  ↓
【总结 + 私域钩子】自然收尾，不是"综上所述"，不硬推
```

**开头的几种方式：**
- 从一个踩坑场景开始："我花了3小时调试这个问题，结果发现..."
- 从一个结论反推："这个工具我用错了6个月，直到上周才搞明白。"
- 从一个观察开始："最近看到很多人问 LangGraph 和直接调 API 的区别，我来说说我的看法。"

## 第七步：长文易读性合同

公众号长文不是研究报告的原样转录，也不是把所有资料都塞进正文。深度要通过清楚的阅读路径交付。

### 7.1 先搭阅读路径

- 一篇 1500-3000 字的文章通常保留 3-6 个 H2 小标题。教程、对比和方法论可以更多，但每个标题必须对应一个读者问题，不能只是“背景”“分析”“总结”这类空标签。
- 开头 150-300 字只完成三件事，交代发生了什么，给出核心判断，告诉读者继续读能解决什么问题。背景资料往后放。
- 每个主要章节开头先说这一节要解决什么，结尾用一句话收束判断或给出下一步。读者只扫标题和每节首句，也应该能复述文章主线。
- 一节只推进一个主要问题。一个章节里出现三个互不相关的判断，就拆节或删掉次要判断。
- 列表、表格和代码块可以使用。它们分别服务于并列比较、决策选择和可复制操作，不得用来替代解释。

### 7.2 控制阅读负担

- 普通段落以 2-5 句为主。超过约 150 个汉字且没有转折、例子或结果的段落，优先拆开。
- 连续出现三段以上抽象判断时，插入一个具体事实、代码、数据、操作结果、真实场景或明确的反例。
- 一个句子只承担一个主要动作或判断。一个句子同时塞进背景、原因、例外、影响和结论时，拆成两到三句。
- 技术术语第一次出现时，先用人话说明它解决什么问题，再保留英文名或正式定义。后文不反复重新定义。
- 每个 500-700 字至少出现一次可感知的东西，真实操作、代码片段、数据、界面现象、失败记录或具体选择。没有材料时缩短文章，不用同义改写填字数。
- 代码块前说明“这段代码解决什么问题”，代码块后只解释最关键的 1-3 个点。完整代码放附件或仓库，正文保留读者真正需要复制或理解的部分。
- 表格只保留会影响选择的维度。超过 6 列或单元格变成小作文时，改成分段比较。

### 7.3 交稿前做一次读者模拟

把自己当成一个知道基本技术、但不了解当前项目背景的开发者，快速扫一遍标题、小标题、每节第一句、代码说明和结尾，检查三件事：

1. 我现在知道文章在解决什么问题吗？
2. 我知道这一节为什么值得读吗？
3. 我能分辨事实、作者判断和待验证信息吗？

任意一项回答“不知道”，先修阅读路径，再修措辞。不要用加粗、感叹号或更多术语掩盖结构问题。

## 第八步：硬性禁区

> 这些是最容易暴露 AI 写作痕迹的地方，绝对避免。

**禁用词（见 qa L1，此处不再重复完整列表）**
核心：禁用所有连接词（首先/其次/综上/换句话说）、感叹式结尾（希望有帮助/欢迎指正）、AI 标志性句式（说白了/意味着什么）。

**禁用标点：**
- 冒号 "：" → 改用逗号或重构句子
- 破折号 "——" → 改用逗号/句号
- 双引号 " " / " " → 用「」或不加

**结构使用边界：**
- 不用连续 bullet point 代替论证。并列选项、步骤、检查清单和字段对比可以使用列表，但列表后要补一句解释它对读者的影响。
- 不要每段都加粗或加小标题。小标题只在帮助跳读和定位时使用，普通段落靠自然转场连接。
- 不把“优点是A，缺点是B，总体来说还不错”的假平衡当作客观。先给适用场景，再明确你的判断。

**禁用假设性例子：**
- 不能编造场景（"比如说有一次..."）
- 没有真实例子就说"我自己还没试过，但我猜测..."
- 要说工具就说具体名字，不说"某个AI工具"
