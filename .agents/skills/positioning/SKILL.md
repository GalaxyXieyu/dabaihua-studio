# Positioning：内容定位下钻

立项任何新内容（单篇/系列/课程）之前，先走这个 Skill。**定位没通过，writer 不许开工。**

> 核心信念：内容定位不是一次想出来的，是被连续质疑"打"出来的。每一层质疑剥掉一层"我们以为读者需要"的假象，露出"读者真实焦虑"的核。
>
> 大部分内容死在第一关：作者想讲什么。这个 Skill 强制你从读者凭什么要看出发。

**融合的方法论来源**：
- JTBD（Tony Ulwick / Clayton Christensen）：读者"雇佣"内容来完成进步，不是消费内容
- April Dunford 定位理论：定位由参照系决定，不是你说什么
- 妈妈测试原则：用户说好的不算，看过去的行为
- 开发者内容策略（Prashant Sridharan, Strategic Nerds）：Help First、四个前提、outside-in 架构
- pi 课程立项实战：六轮质疑逼出真定位的过程

---

## 触发场景

- 要开一个新系列/新课程/新栏目
- 有一个选题但说不清"读者为什么看"
- 写出来的东西总感觉"很技术但跟自己没关系"
- writer 动笔前发现定位模糊，回炉重炼

## 与其他 Skill 的关系

```
positioning（本 Skill）→ 定"给谁看、看什么、为什么看"
    ↓ 通过后才能进入
writer / xhs → 怎么写
visual → 配什么图
qa → 质检
```

**红线**：positioning 文档没产出，下游 Skill 一律不接。

## 分档：多深值得下钻

| 档位 | 适用 | 流程 | 时间预算 |
|---|---|---|---|
| 快版 | 单篇文章 | 收益关 + 焦虑关 | 30 分钟 |
| 完整版 | 系列/课程/专栏 | 五关全走 + deep research | 值得花一下午 |

## 五关下钻流程

### 第 1 关：功能关（5 分钟，快速过）

这个东西能干什么？列出功能清单。

**这一关的答案几乎从来不是卖点，只是素材。** 大部分教程死在这里——把功能清单当内容价值。列完立刻往下走，不要停留。

### 第 2 关：收益关

读者学完能拿走什么？**每条好处必须可兑现、可验证。**

质检问题（逐条过）：
- 这条好处能当天兑现吗？不能的话多久？
- 读者怎么验证自己拿到了？（账单？面试回答？一个能跑的代码？）
- 这条好处是"我能讲的"还是"读者想听的"？（从读者嘴里说出来才算数）

**反例（pi 课程实战）**：最初列的"理解上下文压缩"——读者问"所以呢？"答不上来，砍掉。改成"你的 Agent 跑 20 分钟就失忆？这是工业级解法"——痛点具体，兑现路径明确。

**红线**：所有好处都是"我编的"（没有任何真实用户佐证）→ 必须进第 3 关的 deep research，不许往下走。

### 第 3 关：人群关（含实证）

谁最痛？痛到愿意花时间？**宁可窄而深，不要宽而浅。**

**强制 deep research**（妈妈测试原则：用户说好的不算，看他们过去的行为/原话）：

至少读 3 篇目标社区的真实讨论，引用原话。渠道：
- 中文：linux.do / V2EX / 知乎评论区 / 即刻
- 英文：Reddit / HN / X

记录格式：
```
| 原话 | 来源 | 暴露的真实痛点 |
|---|---|---|
| "Claude Code 想要新功能需要提 issue" | linux.do 帖子 | 对黑盒的无力感 |
```

**人群画像输出模板**：
- 他们是谁：（具体到技术栈+从业阶段，如"2023-24 年学过 LangChain，现在面对 Claude Code 时代感到范式焦虑的开发者"）
- 他们知道什么 / 不知道什么：（两栏列出，差距就是内容空间）
- 他们夜里睡不着的点：（一句话，这是情绪钩子）

**反例**："Agent 工程师"太宽——"应用层 Agent 工程师""AI 全栈""LangChain 一代的范式焦虑者"是三个不同人群，焦虑不同，钩子不同。

### 第 4 关：焦虑关（JTBD 三维度）

JTBD 视角：读者不是"想看内容"，是"雇佣你的内容来完成一个任务"。

**工作必须映射三个维度**（缺一不可，情感和社会性常被忽略）：

| 维度 | 含义 | pi 课程示例 |
|---|---|---|
| **功能性工作** | 要完成的实际任务 | 看懂 Agent 内部架构 |
| **情感性工作** | 想要的感受 | 摆脱"用得很爽但心里没底"的不安 |
| **社会性工作** | 希望被如何看待 | 在同行面前能讲清 Agent 原理，不是只会用工具 |

**JTBD 声明模板**：
> 当 [情境] 时，我想要 [动机]，以便我能 [期望结果]。

pi 课程实例：当 Claude Code 烧了我 600 刀却说不清它为什么这么做时，我想要看懂 Agent 的内部结构，以便我能从"工具的消费者"变成"懂原理的工程师"。

质检问题：
- 读者"雇佣"这篇内容来完成什么任务？（不是"学知识"，是"缓解焦虑/通过面试/省钱/不被时代抛下"）
- 这个焦虑是现在的，还是未来的？（现在的焦虑 > 未来的好处。"总有一天用得上"不是卖点）
- 不看这篇，读者会付出什么代价？
- **情感和社会性工作写出来了吗？**（只写了功能性 = 没戳到痛点）

**关键区分（pi 课程实战）**：
- ❌ "学 pi 将来能自定义 Agent"（未来收益，站不住）
- ✅ "你用 AI 编程越爽，心里越没底——产出变高了，理解变浅了"（当下焦虑，戳中就痛）

### 第 5 关：唯一性关（定位理论 + Help First）

April Dunford：定位不是你说什么，是用户在什么参照系里看你。

**Help First 原则**（开发者内容策略）：开发者怀疑性强、技术成熟、注意力替代选择无限。你通过"先帮助"赢得信任，营销结果自然跟随。**商业回报是信任的自然结果，不是强行推销的产物。**

**开发者内容的四个前提**（每篇必须满足）：

| 前提 | 质检问题 |
|---|---|
| 解决即时问题 | 读者看完能立刻做什么？还是"总有一天用得上"？ |
| 真正教授技能 | 是真教学，还是借教学之名行推广之实？ |
| 尊重智慧 | 把读者当聪明但缺特定上下文的人，还是居高临下？ |
| 提供具体性 | 有真实代码、具体示例、可复现步骤，还是模糊建议？ |

**outside-in vs inside-out 判断**：

| 类型 | 内容方向 | 作用 | 适用 |
|---|---|---|---|
| inside-out | "我的工具多好用" | 服务已有用户 | 留存老读者 |
| outside-in | 读者关心的问题 → 历史背景 → 方案对比 → 引出你的解法 | 获取新用户 | **拉新读者（我们的主战场）** |

pi 课程实例：不讲"pi 多好用"（inside-out），讲"你用 Claude Code 越爽心里越没底——这里有一个开源标本让你看懂"（outside-in）。

质检问题：
- 这个内容如果没有【工具 X】/没有我，还能成立吗？能成立 → 说明没打中唯一性
- 目标读者还会看哪些替代内容？我们的差异化是什么？
- 为什么是现在讲？（时机：范式迁移期/新版本发布/社区情绪窗口）
- 有没有"即将过时"的风险？（如 pi 1.0 重构 → 教概念不教 API）
- 是 outside-in 还是 inside-out？（拉新用 outside-in）
- 四个前提都满足了吗？

**现有内容空位扫描**：搜一圈已有内容，判断：
- 已有人做得很好的（如 pi 的 linux.do 神帖，1022 赞）→ 不重复，直接引用当"课前预习"
- 没人做的（如"为什么这么设计"）→ 这是我们的空位

- 夜里睡不着的点：

- 情感性：
- 社会性：

- [ ] 真正教授技能：

## 系列内容的额外检查（如果是系列，加做）

从 LangGraph 事故复盘固化的纪律：

- [ ] 第 0 篇导读：必须先写，永久置顶，内含完整目录
- [ ] 系列标识进标题：如"（系列名 0X）"，刷到任何一篇都知道有前后文
- [ ] 每篇导航 footer：链接全系列，防孤立
- [ ] 每篇有"可带走的资产"：模板/清单/代码/图——收藏率是核心指标（收藏/点赞 ≥ 1.5 为顶级）
- [ ] 三幕结构检查：颠覆认知（钩新读者）→ 逐层拆解（干货密度，收藏主力）→ 升维实战（成果展示，视频素材）
- [ ] 发布节奏：单日 1 篇，绝不一天多篇

## 实战案例（存档供参考）

历史案例应作为某个内容项目的 `content/projects/<content-slug>/positioning.md` 保存。

六轮质疑的演化路径：
1. "感觉很技术" → 功能清单 → 读者收益
2. "好处是编的" → 推演 → 实证（deep research 拿真实数据）
3. "Claude Code 复杂是为了聪明" → 挑战核心假设 → 发现"自定义"理由站不住
4. "为了学而学" → 寻找真实场景锚点 → 黑盒焦虑
5. "都是区别没好处" → 区别 → 可兑现好处
6. "不够精确" → 人群收窄 → "LangChain 一代的范式焦虑者"

每轮质疑都打在一个真实的假问题上。**定位的直觉就是拒绝妥协。**

## 常见失败模式

| 模式 | 症状 | 解法 |
|---|---|---|
| 功能清单当价值 | "本课程讲 X 的 10 个特性" | 回第 2 关，每条问"所以呢" |
| 编造的好处 | 全程推演无实证 | 强制 deep research，引原话 |
| 未来收益陷阱 | "总有一天用得上" | 找当下焦虑，找不到就换选题 |
| 人群贪大 | "所有程序员都能看" | 收窄到"痛到愿意花时间"的那群 |
| 重复造轮子 | 已有人做得更好 | 引用对方，自己打空位 |
| 只戳功能不戳情绪 | JTBD 只写了功能性工作 | 补情感性 + 社会性工作 |
| inside-out 自嗨 | "我的工具多好用" | 改 outside-in：读者问题 → 方案对比 → 引出解法 |
| 教学之名行推广之实 | 表面教程实为软广 | Help First：真教技能，信任自然来 |
| 笼统无具体性 | "提升效率""优化体验" | 每条必须配真实代码/数字/可复现步骤 |
