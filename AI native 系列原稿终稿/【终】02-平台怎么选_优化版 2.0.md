# AI Agent 平台怎么选？先判断要不要升级，再做三个现场测试

我们把社区数据分析选作第一个 Agent 场景。从提出问题，到分析结论回到工作群，整个流程三周跑通。领导随即决定，照这个模式再铺十个场景。

第二个场景花了两个月。第三个至今还没有完成。

技术上都做得到，真正拖慢进度的是重复建设。每增加一个场景，权限要重新找 IT 申请，数据要重新接，知识文档也要重新配置。第一个场景积累下来的内容，到了第二个场景很难直接复用。

即使把每个场景分别跑通，它们也只是各自完成一段任务。一个 Agent 做完以后，下一个 Agent 不会自动获得前一步的任务目标、背景信息和处理结果，仍然需要人整理后再转交。每个 Agent 使用的知识和口径也各自维护，场景越多，工作标准越分散。

从第一个场景的三周，到第二个场景的两个月，再到第三个场景迟迟没有完成，我们遇到的问题已经不是“能不能搭出一个 Agent”，而是“这些 Agent 能不能接得起来”。

从零到一，场景工具解决得很好。从一个场景复制到十个场景，需要解决的是平台问题。

## 什么时候需要从场景工具升级到平台？

Coze、Dify、WorkBuddy 这类场景工具，帮我们完成了最难的第一步。业务人员能够自己配置，场景可以跑通，也真的有人使用。

但真实业务不会停在一个场景里。它会穿过文档、表格、ERP、OA、CRM 和数据平台，也会经过不同岗位。场景之间没有共同底座，任务一旦走到系统或岗位边界，就要重新申请权限、连接数据、说明上下文、核对工作口径。

上一篇提到的效率断点，在这里变成了更具体的问题。系统之间仍然靠人接手，前一个 Agent 的结果未必能被下一个 Agent 直接使用，权限和审计也跟着场景分散。场景工具解决了单点任务，断点却留在 Agent 之间。

这里所说的平台，不是再增加一个功能更多的搭建工具，而是把跨场景需要反复建设的能力放到一起。系统连接、知识、上下文、工作标准和治理能力可以被多个 Agent 共用，新场景才不必每次从头开始。

但平台解决的是规模化问题，并不是所有团队都需要立刻升级。

按照我们的经验，可以先看三个信号。

第一，场景数超过三个，而且每个场景都要重新配置权限和数据。

第二，有场景需要穿过两个以上的系统。

第三，有场景开始涉及资金操作、对外承诺或敏感数据。

三个信号都没有出现，继续使用场景工具通常更合适。已经出现两个，说明重复建设和治理成本开始超过单点工具带来的便利，可以进入平台选型，但不等于立刻采购或更换。

## 已经跑通的工作方式要不要推倒重来？

第一个场景能够跑通，说明团队已经形成了一套有效的工作方式。升级到平台，不是把现有做法推倒重来，而是让这些做法可以复制到更多场景。

要保住的能力，落在三个环节：Agent 由谁来搭，岗位之间怎么交接，任务在哪里发生。对应到平台上，就是业务仍然能自己配，多个岗位能够接着做，入口仍然留在工作现场。

**业务仍然能自己配。** 职责、技能、知识和工具，可以在配置台上直接选择。配完当场试问，调整后再试。升级到平台后，业务人员仍然要能自行完成配置和调整，不能重新回到提需求、等排期的老路。

**多个岗位能够接着做。** 主理岗位接收任务、组织工作，协作岗位处理边界清晰的专项。不同岗位使用同一份任务背景和工作标准，前一个岗位的结果可以直接交给下一个岗位继续处理。

**入口仍然留在工作现场。** 发布后即可共享，群里的人可以直接 @ 它，过程和结果对团队可见。任务不必转到另一个窗口，后续参与者也能沿着当前上下文继续工作。

Anthropic 内部的 AI 同事 Claude Tag，在 2026 年 6 月公开发布后，展示的就是这种工作方式。

员工在 Slack 群里像 @ 同事一样 @ 它。它读取当前讨论的上下文，在授权范围内完成任务，再把结果发回同一条讨论串。下一个人可以继续安排工作，不用重新搬运背景、进度和结果。

Claude Tag 也没有直接穿过所有企业系统。它能做什么、不能做什么，由管理员按群设置，事后可以追查。先把 Agent 放进真实的工作入口，再逐步扩大权限和参与范围，比一开始追求覆盖所有系统更稳妥。

## 已经沉淀的企业资产要不要重做？

选平台时，还要看规则、知识、岗位配置和审计记录被放在哪一层。要理解这个问题，可以先看 AI Agent 生态的四个层次。

模型层，是大模型本身，一年比一年强。协议层，解决工具如何接入，MCP 是这一层当前的行业标准，第三篇会详细讨论。形态层，决定 AI 以什么方式出现，比如聊天框、IDE 插件、群机器人或直接操作电脑。框架层，是帮助开发者搭建 Agent 的开发框架。

四层之中，框架层受另外三层变化的影响最大。模型能力升级、协议更新或交互形态变化，框架都要重新调整。选择一个过重的框架，也就意味着把长期资产绑定在变化较快的一层。

过去几年，市面上的主流开发框架换了几轮。每一轮出现时，都宣称解决了上一代的问题；模型再次升级后，其中一部分能力又会失效。使用这些框架并非没有收获，团队获得了经验，也承担了重写的成本。框架可以使用，但企业资产不应只依附于某一个框架存在。

选平台时，要看规则、知识、岗位配置和审计记录以什么形式保存。它们能够作为独立数据导出，并通过相对标准的协议连接，更换模型、平台或开发框架时才不需要重新制作。这些资产掌握在企业手里，多个 Agent 也才能持续共享同一套知识和工作标准。

## 原有的 RPA 还能不能继续用？

企业原有的 RPA 不必废弃。规则固定的流程可以继续交给 RPA；需要动态判断的任务交给 AI Agent。RPA 也可以作为一种执行能力或连接器接入平台。

到这里，选型前的清单就明确了：已经跑通的工作方式要保住，企业自己的资产不能被框架锁死；原有工具可以继续使用，也可以根据需要接入平台。

## 什么样的平台值得选？

常见的选型表会比较组件数量、模型数量和界面体验。这些信息能说明产品现在是否好用，却回答不了更关键的问题：团队能不能自己掌握它，增加新的模型、工具或渠道时要改多少，沉淀下来的资产以后能不能带走？

我们内部会做三个现场测试，每个都能当场验证。

**读得完。** 把候选产品的架构、文档、配置方式和关键运行机制交给团队里最懂行的人。能在可接受的时间内弄清楚产品怎么运行，团队才有能力自己定位问题。看完资料仍然理不清运行机制，日常维护和故障处理就只能长期依赖厂商。

**改得少。** 现场接入一个新模型、新工具或新渠道。如果企业确实有需要，也可以测试已有的 RPA 能否作为执行能力或连接器接入。如果只增加一份配置就能完成，新能力可以独立接入；如果必须修改原有内核，每次扩展都会牵动已经上线的场景。

**换得掉。** 要求对方现场说明，如果以后更换平台或开发框架，原有的规则、知识、岗位配置和审计记录是否需要重做。不需要，资产才真正属于企业；需要重做，说明这些资产仍然锁在厂商体系里。

上次评估一家候选方案时，我们把三个测试都跑了一遍。核心逻辑的文档两天读完，及格。接入一个新的取数工具，对方只增加了一个配置文件，也及格。

到了“换得掉”这一步，我们要求岗位配置和知识库能够原样使用。对方当场演示不出来，说要回去排期。截至现在，对方仍未给出答复。

这个结果比功能清单更有用。演示里能做多少功能，只能说明产品当前的能力；当模型、工具和业务要求发生变化时，要重做多少东西，才决定平台能不能长期使用。

功能会过时，低变化成本才是长期能力。

这次选型走到最后，我们真正留下的是两个问题。

多个 Agent 能不能共享连接、知识、上下文和工作标准，沿着同一个业务目标接着工作？

规则、知识、岗位配置和审计记录，能不能在更换模型、平台或开发框架后继续使用？

前一个问题决定多个数字员工能不能真正连起来，后一个问题决定企业积累的能力是否还掌握在自己手里。

平台方向确定以后，下一步才是把企业系统真正接进来。权限、凭证和审批怎么处理，第三篇会继续讨论。这也是整个系列里，我们遇到问题最多的一关。
